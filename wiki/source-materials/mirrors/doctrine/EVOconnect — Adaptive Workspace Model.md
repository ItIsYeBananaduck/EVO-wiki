## Core Idea

> The system adapts its structure to the user, not the other way around.

EVOconnect does not enforce:
- projects
- phases
- tasks
- complex hierarchies

Instead:

> Structure emerges based on user needs, behavior, and task complexity.

---

## Two Primary Domains

### 1. Lifespace

> Personal, ambient, and low-structure domain.

Characteristics:
- minimal structure
- everyday interactions
- personal automation
- smart home integration (future)

Examples:
- reminders
- daily assistance
- home automation
- quick questions

Notes:
- rarely required
- still available if needed
- not central to the experience

---

### 2. Workspace

> Execution and productivity domain.

This is where:
- work happens
- tasks are tracked
- systems are built
- automation is defined

---

## Core Principle — Variable Depth

> Not every user needs the same level of structure.

---

## Low-Complexity Users (Example: Small Business Owner)

User intent:
- “Find this product”
- “Compare prices”
- “Order it”
- “Track delivery”

System behavior:

- No projects
- No phases
- Minimal visible structure

Under the hood:
- tasks still exist
- methods still exist
- execution is still governed

But the user sees:

> Intent → Outcome

---

## High-Complexity Users (Example: Developer / Architect)

User intent:
- multi-phase systems
- structured execution
- long-running projects

System behavior:

- Projects visible
- Phases visible
- Tasks and subtasks visible
- Notes structured across levels

User sees:

> Intent → Structured execution → Outcome

---

## Same System, Different Surfaces

The underlying system is always:

- Task system
- Delegator
- Methods
- Talents
- Notes

But the interface adapts:

| User Type | Visible Structure |
|----------|-----------------|
| Casual / Lifestyle | Minimal |
| Small Business | Light task structure |
| Power User | Full hierarchy |

---

## Invisible Structure Principle

> Structure exists even when it is not shown.

Even for simple users:

- tasks are created internally
- execution is logged
- actions follow lifecycle
- governance still applies

The difference is:

> Visibility, not capability.

---

## Progressive Disclosure

Structure is revealed only when needed.

Examples:

- repeated tasks → suggest grouping  
- increasing complexity → suggest project  
- multi-step workflows → suggest phases  

Alice may say:

> “Do you want me to organize this into a project?”

---

## Notes Across Complexity Levels

Notes behave differently depending on user type:

### Simple Users
- rarely used
- conversational capture
- lightweight

### Advanced Users
- multi-level notes
- linked to projects, phases, tasks
- part of system design

---

## Relationship to Conversational Notes

Notes follow the same adaptive model:

- can exist globally (lifespace/workspace)
- can attach to tasks
- can remain unstructured

Alice determines:
- placement
- relevance
- structure level

---

## Relationship to Task System

All users use the same system:

Created → Reviewed → Approved → Executed → Logged → Completed

But:

- simple users see outcomes
- advanced users see structure

---

## Relationship to Delegator

Delegator enforces:

- safety
- permissions
- execution boundaries

Regardless of user complexity level.

---

## UX Philosophy

> Do not overwhelm simple users.  
> Do not limit advanced users.

The system must:

- feel effortless at low complexity  
- feel powerful at high complexity  

---

## Example Comparison

### Small Business User

User:
> “Find the cheapest supplier and order it”

Alice:
- searches
- compares
- proposes
- executes
- tracks

User sees:
> result + updates

---

### Developer User

User:
> “Plan and execute monorepo migration”

Alice:
- creates project
- defines phases
- tracks tasks
- logs execution

User sees:
> structured system

---

## Core Takeaway

> EVOconnect is not a fixed structure.

It is:

> A dynamic system that expands or contracts  
based on how the user thinks and works.
